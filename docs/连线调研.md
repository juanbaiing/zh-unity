# 连线怎么画才不难看 —— 调研

> 2026-11-04。起因：改了三版（曲线→正交→libavoid+曲线）都丑，使用者说
> 「线根本没连到该有的代码块上」，让我去查别人怎么做的。

---

## 一、先说我到底错在哪

我一直在调「绕不绕、绕多远」，但**业内总结的三个问题，我一个都没处理**：

| 问题 | 表现 | 我的情况 |
|---|---|---|
| **重叠**（overlap） | 两条线走相似路径，画出来像一条，读者分不清是一根还是几根 | **就是它**：三条 `Cube→enemy` 的终点实测完全相同 `[1381,1074]`，画成一根。使用者看到的「没连到该有的块」，就是三条并成一条 |
| **穿节点**（node crossing） | 线从无关节点上穿过去，看起来像连到了那个节点 | 一直在修，修得不彻底 |
| **口歧义**（handle ambiguity） | 多个口的线走相似路径，分不清哪根从哪个口出来 | 没处理 |

来源：[Edge Routing in Workflow Editors: Technical Deep-Dive](https://workflowbuilder.io/blog/edge-routing-in-workflow-editors-technical-deep-dive)

那篇的原话，正是我这几轮在做的事：

> None of these are solvable by asking users to arrange their nodes more carefully.
> They're properties of the routing algorithm, and they require a routing algorithm
> that accounts for obstacles.

## 二、学术怎么说（别凭感觉选形状）

### 最关键的一条：什么因素最影响阅读

Purchase 1997 的结论，被后续研究反复引用：

> edge crossings was「**by far the most important aesthetic**」

其次是**连续性（continuity / 笔直度）**。Ware 2003 量化了：

> 100 度的弯曲（bendiness）让找最短路多花 **1.7 秒**；一次交叉多花 **0.65 秒**。
> **一次交叉 ≈ 38 度的弯曲。**

⇒ 换算下来：**绕远本身不是罪，绕的时候多出来的弯才是**。
一条线为了躲一次交叉而多转 90°，是亏的（90° > 38°）；多转 30°，是赚的。

### 正交 vs 曲线：研究结论是「正交更难读」

- Dwyer 2009（[A comparison of user-generated and automatic graph layouts](https://pubmed.ncbi.nlm.nih.gov/19834160)）：
  > the automatic **orthogonal layout was particularly difficult for users**,
  > even though it had the **fewest edge crossings** of all the layouts.

  交叉最少、反而最难读。原因是正交图里全是 90° 直角弯。
- Purchase 33：正交**本身**被偏好，但**正交图里的 bends** 不被喜欢。

⇒ **曲线优先，直角折线是下策。** 我第二版画直角是对的判断（比第一版规整），但方向选错了。

### 「拓扑」这块

图的**布局**（谁在哪儿）和**走线**（线怎么弯）是两件事。
布局那套叫 layered / Sugiyama 布局（按拓扑层次排队）。走线那套才是 libavoid。
**布局好，走线的活就少一半** —— 现在 `enemy` 八个口全在同一侧、目标在左边，
这是布局留下的坑，路由算法只能绕着填。

## 三、业内的实际参数（这个最有用）

[ComfyUI-NKD-Reroutes](https://github.com/Nekodificador/ComfyUI-NKD-Reroutes) 是专门给 ComfyUI 做「Blender 风格连线」的插件，
把「好不好看」拆成了 11 个可调项。**这套数字比任何理论都直接**：

| 参数 | 默认 | 干什么 |
|---|---|---|
| Wire curvature | 1.0 | 整体圆润度。低=接近直线，高=大弧 |
| **Elasticity** | **1.15** | **短线和长线的差别**。>1 时长线张开、短线收紧 |
| **Distance stretch** | **0.25** | 曲线随距离增长 —— 长线看起来是「拉伸」的，不是扁的 |
| Minimum handle | 10px | 每条曲线的下限。太高 → 所有线一样形状，不管多长 |
| **Handle ceiling** | **0.5** | 上限 = 水平间距的这一比例。调高 → 短线开始打 S 形折返 |
| **Node body clearance** | **24px** | 两个节点挨很近时保留一点弯，线不会缩成一条边 |
| **Socket stub** | **0–60px** | **离开 socket 的直线尾巴**，之后才开始弯 |
| **Invert on backward** | **on** | **反向走线卷成 C 形环，而不是横切节点** |

### 它不用设置就自带的三件事（正是我缺的）

> - Wires leaving the same side of a node **fan out into their own lanes** instead of stacking.
> - Wires running between the same two nodes travel together as a **ribbon**, in parallel, never crossing each other.
> - Unrelated wires that end up sharing a corridor are **spread apart** so they do not draw on top of one another.

翻译：

1. **同一侧出去的多条线分到各自的车道**，不许叠在一起
2. **同一个源→目标之间的多条线走成平行的缎带**，彼此不交叉 ← 直接解决我的「三条并成一条」
3. **共享走廊的无关线分开**，不许画在对方身上

## 四、所以该怎么做（提案，未动手）

### 主线：不做全局正交路由

libavoid 那套（可见性图 + A*）**算得对但画出来难读** —— 它给的是直角折线，
而且为了避障会绕远。用户的观感已经证明了这点（「更丑了」）。

改成 **参数化贝塞尔 + 局部分道**：

| 做 | 怎么 | 治哪个病 |
|---|---|---|
| 1. **同侧出口分道** | 从一个节点同一侧伸出的 n 根线，在 y（或 x）上按 `i - (n-1)/2` 分散开，间距 ~6px | 八个口挤成一根 |
| 2. **同源同目标做缎带** | 同一个 (源, 目标) 对之间的 k 根线，整条路径偏移 `i * 6px` | 三条 Cube→enemy 并成一根 |
| 3. **socket stub** | 从口出来先走 10~14px 直线，再开始弯 | 线从口里「长」出来的感觉 |
| 4. **反向走 C 环** | 目标在源的后方时，控制点朝外甩成 C 形，不横切节点 | enemy→Cube 绕大圈 |
| 5. **elasticity + 上限** | 控制点长度 = `clamp(距离 × 0.5, 20, 水平间距 × 0.5)`，短线收紧 | 长线拉伸、短线不折返 |

### 不建议继续走的路

- 调 libavoid 的 `bendPenalty` / `edgeSpacing` 去凑 —— 我试了 55 / 320 / 70 三档，
  55 出迷宫、320 出大回环、70 折中，都不对。**问题不在参数，在「正交形状本身难读」**。
- 把端点推到框边界 —— 会让线绕更远（试过）。

### 一条要单独确认的

`enemy` 的八个口**全在框的右侧**，而目标在左边。
不管算法怎么好，这都逼着线绕。要么接受，要么**把口分到框的两侧**（左右各一半）。
这是布局问题，不是走线问题。
